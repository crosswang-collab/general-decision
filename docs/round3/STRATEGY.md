## 0. 結論（30 秒版）

1. **推薦重複是固定行為，不是偶發。** 程式從頭到尾沒有隨機性，也沒有記憶：同一個座標每次都拿到同一份 Google 熱門清單，程式依評分排序，prompt 又叫模型挑第一名，模型挑不出來時伺服器也指定第一名。Round 3 把選店權從模型收回程式，改成「沒去過優先＋可控新鮮度＋品質保底」的加權抽樣。
2. **價位要做成「金額 chips」，依所在國家切換台幣／日圓。** 篩選採兩層：Google 有價位資料就照資料篩，沒有資料就降權並標「價位未知」，不直接剔除。
3. **回饋不另開新流程，沿用現有三顆鍵再加原因。** 完成就記為「去過」；換口令改成先選原因；登記畫面多一顆「列入愛店」。記憶只存 `place_id` 與時間戳。
4. **前百名級的關鍵是真功能夠硬**（R2§0-1、R1§4）。所以本輪先把「發掘」做成看得見的價值：班長說得出「這家你沒去過」，週報算得出「本週新占領 N 個據點」。上架只做本機能完成、能驗證的部分；原生打包與送審留到下一輪。

## 1. 定位與指標

### 1.1 一句話定位

> **「打開它，班長替你在附近挑一家你還沒去過、但不會踩雷的店，下令，你照做。」**
> 對手是「要自己看清單」的地圖與評價 App（R1§2.3 引 NYT：「我要有人替我選」），也是「隨機但不懂你」的轉盤 App（R1§2.2：轉盤的不重複得手動勾選，沒有一個會自動記住你去過哪）。決斷連的差異點有三個：真店、會記得你、一次只給一個答案。

### 1.2 北極星指標

**每週被服從的口令數（Weekly Obeyed Orders, WOO）**＝每週回報「完成」的口令總數。

- 為什麼選它：口令被服從，代表決策真的被接手，使用者也真的出門了。這把三件事綁在一起：打開、相信、行動。只算打開次數會獎勵「看了不照做」；只算新店數會獎勵「亂推」。
- 怎麼量（無帳號、無 DB）：伺服器端 `/api/order` 每次記一行匿名 log，內容是 `mode`（new／revisit／wildcard）與「這家店過去 14 天是否出現過」，不記 place_id、不記座標。完成率在本機 `diary.ts` 計算，週報 `stats.complianceRate` 已有欄位。外部遙測本輪不做（見 §4）。上線前先用除錯畫面（`app.tsx` 的 Debug）人工讀取。
- 拆解：WOO＝週活躍人數 × 每人每週口令數 × 服從率。本輪主攻後兩項：推薦不再重複，人就會多按；推薦可信，人就會照做。

### 1.3 三個護欄指標（任何一項破線，就不准用北極星的成長當理由上線）

| # | 護欄 | 門檻 | 為什麼 | 量法 |
|---|---|---|---|---|
| G1 | **新鮮度**：`eat` 在同一地點 14 天內的同店重複率 | 7 天內重複率 < 15%；14 天 12 餐中不重複店數 ≥ 9（R3§2.4） | 直接對應老闆抱怨 (1)，不能靠北極星間接推論 | 離線重播＋伺服器匿名 log |
| G2 | **品質保底**：被選店的平均貝氏評分降幅，以及「這家不要再來」的比率 | 平均評分比舊版低 ≤ 0.15（R3§2.4）；「不要再來」原因 ≤ 10% | 發掘不能變成踩雷。R3§1.1 對 serendipity 的定義是「意外**且相關**」 | 離線重播＋本機回饋統計 |
| G3 | **可靠與成本**：「店關了」回報率、p95 端到端延遲、每道口令的 Places 呼叫數 | 「店關了」≤ 5%；p95 ≤ 6 s；Places 呼叫 ≤ 2 次／口令 | 擴大候選池會增加呼叫與延遲；愛食記「歇業未下架」是重複出現的差評（R1§2.2） | 現有 `[timing]` log、`x-places-calls` header、本機回饋 |

## 2. 根因診斷：為什麼同一個位置永遠是同一家

整條鏈從頭到尾都是**確定性**的（沒有任何亂數），而且**跨次沒有記憶**。逐層說明：

| 層 | 位置 | 現況 | 後果 |
|---|---|---|---|
| ① 候選來源固定 | `api/order.ts:242`、`places.ts:21`、`cards.ts:15`、`places.ts:53-55` | 「吃」（非甜食）走 Nearby，`includedTypes: ['restaurant']`，`maxResultCount: 15`，**沒有帶 `rankPreference`**。Google 預設依 POPULARITY 排序，而且 Nearby 沒有分頁（R3§0-1b、§1.3） | 同一個座標每次拿到同一批 15 家熱門店。GPS 飄移幾十公尺也不會改變結果 |
| ② 本地依評分固定排序 | `places.ts:126-129`（貝氏平均）、`places.ts:168`（sort）、`places.ts:169-170`（只留 ≥4.0 且 ≥10 則，再 `slice(0, 8)`） | 同分時看步行距離，仍然是確定性排序 | 候選清單的順序每次一樣，第 1 名每次一樣 |
| ③ prompt 叫模型挑最高分 | `prompt.ts:30`（規則 6「優先挑評價數多且分數高」）、`prompt.ts:58`（「候選店家（已依評價排序…）」＋編號 1–8） | 模型（Haiku）照字面做，幾乎每次挑第 1 名 | 模型等於 `argmax(rating)`，只是多花了 3–6 秒 |
| ④ 備援也指定第一名 | `api/order.ts:115-121`（重打一次後仍沒對到 → `places[0]`） | 伺服器端的保底仍是評分最高那家 | 沒有任何一條路徑會產生變化 |
| ⑤ 排除名單只活在單次操作 | `app.tsx:46`（`useRef`）、`app.tsx:104`（每次進 intake 就清空）、`app.tsx:153-154`（只有按「店關了」才加入，一道口令最多換 1 次）、`types.ts:37` | `exclude` 只在「同一次換口令」有效 | 關掉 App 再開，排除名單歸零 |
| ⑥ 歷史只有店名，模型也只拿來調侃 | `diary.ts:53-58`（`recentOrders` 只傳 `big`，沒有 place_id）、`cards.ts:19`（「點出這週第幾次」）、`prompt.ts:61` | 近 7 天紀錄是笑話素材，不是排除條件 | 班長知道你這週吃了 3 次，還是叫你去第 4 次 |
| ⑦ 被拒絕與被看過的店沒有留下紀錄 | `diary.ts:17-24`（同 id 覆寫）、`app.tsx:78-84,155` | 換口令後，第二家會覆寫第一家；只看了口令沒回報就關 App，什麼都不記 | 系統連「推薦過什麼」都不知道，不可能做到不重複 |

**次要問題（不是重複的根因，但本輪一併修，因為日本情境會直接出錯）：**

- `places.ts:119-120` 的 `hhmmTaipei` 把「HH:MM 開」寫死成台北時區。在日本會差 1 小時。
- `places.ts:100-102` 的 `closingTime` 用 `now.getDay()` 判斷星期幾，這是**伺服器時區**（Vercel 是 UTC）。台北 00:00–08:00、東京 00:00–09:00 之間會拿到前一天的營業時間。
- `api/order.ts:241-242` 的 `languageCode` 固定為 `zh-TW`。在日本，店名可能被翻成中文，跟招牌對不上（屬假設，需實測）。
- `src/locale.ts` 會把「地鐵」一律換成「捷運」，在東京會說錯。
- 使用者選的「忌口：素」只寫進 prompt（`cards.ts:10`），沒有影響查詢類型，所以候選池裡可能沒有任何素食店。
- `FIELD_MASK`（`places.ts:6-16`）沒有 `priceLevel`、`priceRange`、`types`，價位與連鎖判斷都缺資料。

**結論：** 只改 prompt 或只加亂數都不夠。R3§0-1 的三層（池子固定、排序與 prompt 偏向最高分、沒有記憶）要**一起修**，還要補上第 ⑦ 層「推薦過的店要寫下來」。

## 3. Round 3 必做清單

排序規則：**A 直接解決老闆的兩個抱怨 → B 前百名級體驗 → C 上架準備**。同一組內依相依順序排列。

### A. 直接解決兩個抱怨

#### A1　發掘引擎：店由程式決定，班長只負責講

- **為什麼**：§2 的 ②③④ 三層都源於「模型或排序選店」。R3§0-2 建議「店由程式決定，Claude 只寫口令」，做法是 Thompson 式品質抽樣、近期曝光指數衰減、連鎖降權、加權隨機。R1§5-2 結論相同，並明說 `prompt.ts` 規則 6 要刪。另一個附帶效益：模型不必從 8 家裡挑，prompt 變短，「沒挑到真店→重打」（`order.ts:99-122`）這條路徑幾乎消失，延遲也會下降。
- **做法要點**（參數用 R3§2.2 的起始值，不重新發明）：
  - 新增純函式 `pickPlace(cands, mem, prefs, rng)`（放 `src/discovery.ts`），流程依序為：硬過濾 → 打分 → Efraimidis–Spirakis 加權抽樣。亂數來源 `rng` 可注入，測試時用固定種子。
  - 新增本機記憶 `PlaceMem`（IndexedDB，**跟 diary 分開存**，避免 §2⑦ 的覆寫問題），**只存 `place_id` 與自己的事件時間戳**（R3§3.3：place_id 可以無限期保存，店名與評分不可以）。
  - **拿到口令的當下就記一次 `shown`**，不必等使用者回報（修 §2⑦）。
  - `OrderRequest` 加 `mem`（最近 200 筆摘要，約 6 KB）與 `prefs`；伺服器維持無狀態。
  - prompt 改成「店已決定：{名稱}，mode={new|revisit|wildcard}，只負責寫口令」。刪掉 `prompt.ts:30` 的「優先挑評價…」和 `prompt.ts:58` 的「已依評價排序」與候選清單。
  - `order.ts:115-121` 的保底改成用 `pickPlace` 的結果覆寫，不再用 `places[0]`。
  - **可控新鮮度**：設定一個持久的「偵察方針」，三段，從首頁班長名牌旁進入，**不放進每次的 intake**：

    | 方針 | 參數（起始值） | 使用者感受 |
    |---|---|---|
    | 熟門熟路 | λ=0.6、wildcard=0、愛店 ×2 | 大約一半回老地方 |
    | 均衡（預設） | λ=1.2、wildcard=0.2（R3§2.4） | 約 7 成是沒去過的店（R1§5-2） |
    | 全面偵察 | 只抽曝光為 0 的店，排除連鎖 | 一律新店；附近都去過時，班長宣布「這區已全數占領」，並自動把半徑放大一圈 |

  - 範圍：`eat` 與 `rest` 都用 Places，都套用這套引擎（成本一樣，`rest` 的 Text Search 依距離排序，一樣會重複）。`go`、`travel` 不查 Places，不在範圍內。
- **使用者看得到的行為**：同一個地點連按幾天都是不同的店；口令會說「這家你沒去過」或「第 3 次來，准」；附近都吃過時，班長會明講，而不是一直重推。
- **驗收**：
  1. 單元測試（固定種子）：被標「不要再來」的店 100% 不出現；最近 3 次出現過的店 100% 不出現；低於品質保底的店 100% 不出現。
  2. **離線重播腳本**（`scripts/replay-discovery.mjs`，用合成的候選池：40 家、評分與評論數分布擬真，不用 Google 真實資料，見 §6 R4）：模擬 14 天 × 每天 2 餐，三種方針各跑 200 次，結果要達到 G1、G2 的門檻，而且「評分前 3 名店的占比 < 50%」（R3§2.4）。
  3. 正式站實測：在同一座標連續要 10 次「吃」口令，全部回報完成，至少拿到 8 家不同的店。
  4. 模型被重打的比率（`dbg.retry=noplace`）比改版前下降。

#### A2　擴大候選池：細類輪替，每次 ≤ 2 次 Places 呼叫

- **為什麼**：R3§1.3 寫明「池子只有同樣 8 家，演算法救不了」。Nearby 最多 20 筆、無分頁，但輪替 `includedTypes` 與 `rankPreference`，每種組合會撈到不同的 20 家。
- **做法要點**：
  - 每次查詢由 A1 的細類偏好（Beta 抽樣，25% 改成均勻隨機）挑 1 條路線（lane），例如 `ramen_restaurant`、`taiwanese_restaurant`、`japanese_restaurant`。`rankPreference` 在 POPULARITY 與 DISTANCE 之間交替。`maxResultCount` 從 15 調到 20。
  - 第一條 lane 撈到的有效候選少於 5 家，才發第 2 次呼叫（`restaurant`＋DISTANCE 作為廣域後備）。
  - 「忌口：素」改走 `vegetarian_restaurant` lane，修 §2 次要問題。
  - `FIELD_MASK` 加 `places.types`、`places.priceLevel`、`places.priceRange`。R3§0-3 指出這三個欄位都在 Enterprise SKU，跟現有欄位同一級，**SKU 等級不會變**。
- **使用者看得到的行為**：今天被派去拉麵、明天被派去台菜，而不是永遠是附近最紅的那家。
- **驗收**：每一條 lane 的 type 都在正式 key 實測過，回 200、不是 400（R3§1.3 明說新 type 沒驗證過）。lane 表裡的每一項都要附實測結果。`x-places-calls` 第 95 百分位 ≤ 2。

#### A3　價位篩選（台幣／日圓）

- **為什麼**：老闆抱怨 (2)。R1§3 說明 Google、Yelp、OpenTable、ホットペッパー都把價位當標配篩選。R3§3.2 的限制：Text Search 有 `priceLevels`，Nearby 沒有；台灣、日本的價位資料覆蓋率**查不到**。
- **做法要點**：
  - `eat` 的 intake 加一列「預算」，**每人每餐**。用金額文字，不用 `$$$`（R3§4.4：台日沒有 `$` 的共識）。
    - 台灣：`不限`（預設）／`≤150`／`150–400`／`400–1,000`／`1,000+`
    - 日本：`不限`／`〜¥1,000`／`¥1,000〜2,500`／`¥2,500〜6,000`／`¥6,000〜`（切點見 R3§4.2）
  - 國家由**座標**判斷（或 `priceRange.currencyCode`），**不看手機語系**（R3§4.3）。在東京的台灣使用者，自動看到日圓。
  - `IntakeField` 擴充多選型（`types.ts:9` 目前只有單選 `chips`／`stars`）。可以多選，但只能選相鄰檔位（選 1 和 3 會自動補上 2）。記住上次的選擇。午餐時段隱藏最高檔。
  - 篩選分兩層（R1§5-3、R3§4.3）：用 `bandOf()` 把 `priceRange`／`priceLevel` 換算成檔位，在本地過濾。命中的店權重 1.0，相鄰檔 0.35，價位未知 0.5。**價位未知的店不剔除，但口令卡上標「價位未知」**。附近找不到符合價位的店時，不硬塞；班長請使用者確認放寬一檔（R3§4.4）。
  - 模型只拿到檔位文字，**不准自己生出金額**。由 `enforceRules` 保證：口令裡出現金額，就必須來自資料。
  - 遙測：伺服器 log 記錄每次候選中「有價位資料」的比例，依國家分開。第一週如果 < 40%，就改用細類推估，並標「價位推估」（R3§4.3）。
- **使用者看得到的行為**：在台北點 `150–400`，派到的是定食、麵店，不會是鐵板燒；到東京打開，chips 自動變成日圓。口令卡顯示「≈NT$200–300」（直接引用 Google 回傳值，不落地保存）。
- **驗收**：`bandOf` 單元測試涵蓋 TWD、JPY、無上限、只有 `priceLevel`、無資料五種情況。座標在東京時 chips 顯示日圓（E2E 用假定位驗）。重播中選「≤150」時，命中檔位或價位未知的店占比 ≥ 95%。模型輸出出現資料以外的金額時，`enforceRules` 測試要能攔下。

#### A4　回饋：去過／不喜歡／愛店

- **為什麼**：R3§2.3 把每種回饋事件對應到不同的記憶更新。R1§5-1 指出現有的「完成／店關了／沒做」三種回報已經能當訊號，不必新增流程。R1§4-4 說明「使用者自己的紀錄就是資產」（Beli、Swarm、食べログ）。
- **做法要點**（每一項都不超過 1 次額外點擊）：
  - **完成**＝去過：記 `done`；這個細類的偏好分數 `a += 1`。
  - **換口令**改成先跳出原因（底部選單，三選一，只點一下）：
    - 「店關了」：這家 24 小時內不再出現，**不扣**細類偏好。
    - 「今天不想吃這類」：這次操作中，同細類權重減半；細類偏好 `b += 0.5`。
    - 「這家不要再來」：90 天不出現；第二次標記就永久不出現。
    - `cards.ts:20` 的 `reissueLabel` 改成「換一家」，原因放進選單。
  - **愛店**：登記畫面（LogScreen）多一顆「列入愛店」。日記中的店家紀錄長按，可以「列入愛店／不再推薦」。愛店在「熟門熟路」方針下權重加倍，在「均衡」下可當回訪的那三成。
  - 「沒做」（罰則）**不算**不喜歡，不改店的權重。不服從是行為問題，不是店的問題。
  - 一道口令最多換 1 次的規則保留（`app.tsx:154`），維持「不可拒絕」的人設（R1§5-5）。
- **使用者看得到的行為**：說過不要的店，三個月內不會再看到；按過愛店的店，會在「熟門熟路」時回來。
- **驗收**：每種回饋事件對 `PlaceMem`／細類統計的影響都有單元測試。E2E 驗證：換口令 → 選「這家不要再來」→ 第二道口令不是同一家，關掉 App 重開後仍然不會出現。

#### A5　連鎖店處理

- **為什麼**：R3§1.2 指出 Google 的 Place 資料**沒有**連鎖或品牌欄位。不處理的話，「發掘」會被麥當勞、すき家這類店稀釋，同品牌不同分店也會變相重複。
- **做法要點**：
  - 判定分三層：① 自建品牌字典（台灣＋日本各 50–100 個常見品牌，屬於我方資料，不是 Google 內容）；② 同一批候選中，去掉分店字尾（「○○店」「〜店」）後前綴相同的 ≥ 2 家視為同一品牌；③ 選配：工作目錄中尚未進版控的 `src/jevJudge.ts` 已經寫好連鎖判斷題，可以當第三層，但**不得成為必要依賴**（失敗就退回 ①②）。
  - 規則：連鎖店權重乘 0.6（R3§2.2）；**同品牌的曝光合併計算**，今天去摩斯 A 店，明天就不會被派去摩斯 B 店；「全面偵察」方針完全排除連鎖；但附近只剩連鎖時仍可推薦，避免無店可派。
- **使用者看得到的行為**：口令卡不會連續兩天出現同一個品牌。
- **驗收**：字典與聚類的單元測試，例如「八方雲集 南京店」和「八方雲集 復興店」要判為同一品牌，「すき家 渋谷店」要判為連鎖。重播結果中，連鎖店占比 ≤ 候選池中連鎖占比 × 0.7（R3§2.4）。

### B. 前百名級體驗

#### B1　「班長記得你」：讓發掘被看見

- **為什麼**：R2§6-1 認為「班長記得你」是人設與功能互相強化的最佳交會點。R3§1.1 說「這家你沒去過」本身就是 serendipity 裡「refreshing」的那一部分。R1§5-4 建議把「發掘」變成看得見的進度。
- **做法要點**：
  - 每種 mode 都有必須出現的語意，由 `enforceRules` 檢查，不合格就換成內建語料：new 要提到「沒去過／新據點」，revisit 要提到「第 N 次」（N 由程式算好給模型），wildcard 要提到「偵察」。
  - 新兵日記與莒光園地週報加兩個數字：「本週新占領 N 個據點／回防 M 次」。週報 prompt 拿到這兩個數字，只負責評論，不負責算。
- **使用者看得到的行為**：班長的話會反映你的歷史。週報第一行就是你這週的探索成績。
- **驗收**：三種 mode 各 20 次 mock，語意檢查 100% 通過（不通過的會被替換成語料）。週報的數字跟本機 `PlaceMem` 算出來的一致。

#### B2　日本情境正確性

- **為什麼**：老闆在台灣和日本都會用。R2§0-5 指出台日不能共用一套假設。§2 次要問題裡，時區、星期、「捷運」三項在日本會直接說錯，這是品味原則 T9 的硬性失敗。
- **做法要點**：
  - 時區由座標判斷（台灣用 Asia/Taipei，日本用 Asia/Tokyo），用來修正 `places.ts:119-120` 和 `places.ts:102`。
  - 「地鐵→捷運」替換只在台灣生效；在日本改用「電車／地下鐵」。
  - 店名語言：實測 `languageCode` 用 `zh-TW` 和 `ja` 時，日本店名的差別。如果中文譯名跟招牌對不上，就在日本改顯示日文原名，班長台詞仍用台灣繁中。
  - 介面維持台灣繁體中文，**不做日文介面**（見 §4）。
- **使用者看得到的行為**：在東京，「11:30 開」是當地時間，金額是日圓，店名跟招牌一致。
- **驗收**：單元測試固定 `TZ=UTC`，對東京和台北座標各測 00:30、08:30、23:30 三個時間，`closingTime` 和 `opensAt` 都要正確。locale 測試：日本座標的口令不出現「捷運」。

#### B3　火力旋鈕：專業模式

- **為什麼**：R2§0-2 指出毒舌必須能關掉（CARROT 最低一檔是 professional）。這也能降低 Apple 審核 1.1.1 的風險（R2§3）。現在只有三位班長，沒有「不罵」的選項。
- **做法要點**：在三位班長之外加一個「文書兵」：口令照下，meme 的上下兩行改成中性描述，罰則改成溫和版本。只有靜態語料與 prompt 改變，**不新增角色圖**（如果要用現有素材當中性頭像，需要另外確認）。
- **使用者看得到的行為**：長輩或不喜歡被罵的人，也能用同一套決策功能。
- **驗收**：專業模式 50 次 mock 輸出，`banned.ts` 字表 0 命中，且不出現「菜」「屁股」等罵行為的詞。

#### B4　速度與錯誤路徑

- **為什麼**：「一次只給一個答案」的價值，在於比自己滑地圖快（R1§2.3）。A2 可能多一次 Places 呼叫，所以要靠 A1 縮短 prompt 來扣回時間。
- **做法要點**：改完後 prompt 不再帶候選清單，`max_tokens` 下修。Places 的兩次呼叫只有在第一條 lane 不夠時才發，而且不能並行，以免浪費額度。
- **驗收**：正式站 20 次「吃」，p95 ≤ 6 s（G3）。

### C. 上架準備（只做本機能完成、能驗證的）

#### C1　隱私與 Google 條款合規

- **為什麼**：R3§3.3 指出 Google 條款列舉禁止「copy and save business names」；`diary.ts`／`types.ts:80` 現在會存 `placeName`。R2§3 提到 5.1.2(i)：資料分享給第三方 AI 之前，必須明示並取得同意。R3§3.3 的歸屬規定：不在 Google 地圖上顯示 Places 資料時，要標「Google Maps」。
- **做法要點**：
  - 新寫入的日記只存 `place_id`，顯示時改用當次口令的店名。舊資料的處理方式（保留／刪除／重取）**要先請 Cross 決定，並由法務或 Google 確認**，本輪先停止新寫入。
  - 口令卡加上「Google Maps」文字歸屬，帶 `translate="no"`。
  - 第一次使用時顯示同意畫面：說明位置會送 Google、選擇與記憶摘要會送 Anthropic，記憶只存在手機上。
  - App 內加隱私政策頁，靜態頁即可。
- **驗收**：用 grep 確認 IndexedDB 寫入路徑中沒有店名、評分、座標欄位（座標最多存 30 天，本輪乾脆不存）；E2E 驗證首次啟動會出現同意畫面，同意之前不會呼叫 `/api/order`。

#### C2　沒有定位時的手動地點

- **為什麼**：R2§3 引 5.1.1／5.1.5：使用者不給定位時，App 必須提供替代方案。現在的做法是直接報錯（`app.tsx:124-127`）。
- **做法要點**：錯誤畫面加「手動報座標」，輸入車站或地標名稱，伺服器端用 Text Search 換成座標，不在本機保存。
- **驗收**：E2E 拒絕定位 → 輸入「台北車站」→ 拿到一道附近店家的口令。

#### C3　檢舉不當口令與伺服器端輸出過濾

- **為什麼**：R2§3 提到 1.2：AI 生成內容類 App 需要過濾、檢舉機制與公開聯絡方式。現在的 `banned.ts` 只是字表。
- **做法要點**：口令卡加「回報這道口令」，用 mailto 或表單即可，**不需要後端 DB**。在 `enforceRules` 之後，伺服器端再跑一次 `banned.ts` 檢查，命中就換成語料。
- **驗收**：故意把禁詞放進 mock 回應，送到前端的版本 0 命中。

#### C4　上架素材與「Capacitor-ready」

- **為什麼**：R2§5 的必要清單。4.3(b) 的差異化論述要靠 A1–A4 才有實質內容（R2§0-3）。
- **做法要點**：
  - 寫 `docs/round3/STORE-LISTING.md`：台灣與日本的名稱、副標、關鍵字（實測 ≤ 100 bytes）、審核備註（無需登入、人設設計、「罵行為不罵人」、與轉盤 App 的差異）。
  - 程式碼保持能用 Capacitor 打包本機資源的狀態：不依賴 `server.url`，Web Share 與定位都先做功能偵測。
  - **本輪不做**實際打包與送審。
- **驗收**：關鍵字欄位用 `Buffer.byteLength` 實算 ≤ 100；審核備註逐條對應到 R2§5 的必要 1–8，列出哪些已完成、哪些還缺。

### 本輪相依順序（給施工者）

`A2 的 FIELD_MASK 與 lane 實測` → `A1 的 PlaceMem＋pickPlace＋prompt 改寫`（同時修 §2⑦） → `A4 回饋` → `A5 連鎖` → `A3 價位`（需要 A2 的欄位） → `B2 日本` → `B1 文案與週報` → `B3`／`B4` → `C1–C4`。
每個階段交付前都要跑完 DEV-PLAN-2 §3 的驗證閘門（typecheck、unit、build、check:bundle、e2e），另外加跑 A1 的離線重播腳本。

| 項目 | 不做的理由 |
|---|---|
| 帳號、登入、雲端同步 | DEV-PLAN-2 §1 規則 5 明文禁止。記憶在本機就足以解決抱怨 (1)。代價是換手機或清除資料時記憶會消失，列入 §6 風險 |

| 主動跳出評分請求 | 3.2.2(x) 禁止強迫評分；R2§4 也指出日本使用者反感隨意跳出的評分視窗。留到上架那一輪，挑「完成口令＋升階」這種好時機 |

## 5. 品味原則（Taste principles）

每一條都可以判定 PASS／FAIL。新功能與文案上線前要逐條自查。

| # | 原則 | PASS 條件（任一條不成立即 FAIL） |
|---|---|---|
| T1 | **一道命令，一個答案** | 口令畫面上只有一家店、一組步驟。不出現「或」「也可以」「備選」，也沒有清單。用 grep 檢查語料與 mock：0 命中 |
| T2 | **店由程式決定，班長只負責講** | 在相同的種子與輸入下，最終的 `place.id` 100% 等於 `pickPlace` 的輸出。模型回傳任何別的店都會被覆寫 |
| T3 | **新，要說出來；舊，要數出來** | mode=new 的口令含「沒去過／新據點」語意；revisit 的口令含程式算好的「第 N 次」。由 `enforceRules` 檢查，通過率 100%（不合格就換成語料） |
| T4 | **驚喜，但不踩雷** | 不論哪種方針，被選的店都要貝氏評分 ≥ 3.7 且評論數 ≥ 5；放寬時要記 log。重播中 0 筆低於保底 |
| T5 | **控制只多一下點擊** | 「吃」的 intake ≤ 3 列，每列 ≤ 5 個 chips，沒有文字輸入框。在 375×667 畫面上不捲動就按得到送出鍵。點擊目標 ≥ 48 dp（R3§4.4 引 M3） |
| T6 | **數字一律照實，不編** | 價位、步行分鐘、營業時間、第 N 次，全部來自 API 或本機紀錄。口令裡的金額或時間如果在資料中找不到，就是 FAIL（`enforceRules` 測試覆蓋） |
| T7 | **罵行為，不罵人；命令本體零毒性** | `steps`／`place`／`log` 的 `banned.ts` 命中為 0，罵只出現在 meme 的上下兩行。專業模式下全部欄位都是 0（沿用第 7 節七條規則） |
| T8 | **拒絕要付代價，但每個拒絕都讓班長變聰明** | 每道口令最多換 1 次；每一個換口令原因都會改變 `PlaceMem` 或細類統計（測試逐一斷言）。沒有「無限重抽」 |
| T9 | **在哪裡就照哪裡的規矩** | 用日本座標測試時，0 筆出現 NT$、「捷運」或台北時間；用台灣座標測試時，0 筆出現 ¥ 或日本用語。介面文字一律用台灣用語（沿用 `locale.ts`） |
| T10 | **3 秒內知道往哪走** | 口令畫面不捲動就能看到：店名、步行分鐘、營業到幾點（或幾點開）、價位檔（或「價位未知」）、地圖按鈕。缺任何一項就是 FAIL |

## 6. 風險與假設

### 風險

| # | 風險 | 影響 | 對策 |
|---|---|---|---|
| R1 | 台灣與日本的 `priceLevel`／`priceRange` 覆蓋率**查不到**（R1§3、R3§3.1） | 價位篩選看起來沒效果，或大量店被標「價位未知」 | 不硬性剔除；第一週先量覆蓋率；< 40% 就改用細類推估並標示（R3§4.3） |
| R2 | 新的細類 type 沒經過實際呼叫驗證，可能回 400（R3§1.3） | 整次查詢失敗 | 每條 lane 先在正式 key 實測，失敗就從 lane 表移除；執行中遇到 400 自動退回 `restaurant` |
| R3 | 演算法參數沒有經過模擬（R3 開頭的聲明） | 太保守會讓重複問題繼續；太激進會踩雷 | 用離線重播校正 T、λ；正式站另外留一個偵察方針可以手動調整 |
| R4 | 離線重播不能用 Google 真實資料（條款禁止保存店名與評分，R3§3.3） | 重播結果和真實分布有落差 | 用合成的候選池（分布參數取自除錯畫面的匿名統計），再加 §3 A1 驗收 3 的正式站實測 |
| R5 | 記憶只存在本機。換手機、清除 Safari 資料、**將來從 PWA 換成 Capacitor（origin 不同）**都會讓記憶消失 | 「班長記得你」突然失憶 | 下一輪做「匯出／匯入記憶」（place_id JSON）；換到 Capacitor 時寫轉移流程 |
| R6 | 新鮮度可能反而降低滿意度：吃飯本來就會回訪（R3§1.2 RepeatNet） | 服從率下降 | 預設「均衡」保留約三成回訪；愛店；方針可調；用 G2 與服從率監看 |
| R7 | 第 2 次 Places 呼叫增加成本與延遲 | G3 破線、每日上限（`places.ts:27` 是 40 次）提早用完 | 只有在候選不足時才發第 2 次；G3 監看；必要時把上限換算成「每日口令數」 |
| R8 | Haiku 不照 mode 寫，或在口令中提到別家店 | T2／T3 FAIL | `enforceRules` 覆寫店名並做語意檢查，不合格就換成語料（DEV-PLAN-2 規則 9） |
| R9 | Apple 4.3(b) 可能把它歸為「今天吃什麼」的成熟品類而拒絕（R2§0-3） | 被退件 | 審核備註強調真店、記憶、週報、發掘數據；這也是 A1–A4 放在上架之前的原因 |
| R10 | 日記 `placeName` 的條款風險**無法在本輪下結論**（R3§3.4） | 合規 | 先停止新寫入，舊資料怎麼處理交給 Cross 與法務決定 |
| R11 | 匿名 log 在 Vercel 免費方案保留時間很短（README、`types.ts:51-55` 已提到） | 指標斷層 | 每週人工匯出一次；或下一輪接 log drain（需要評估隱私） |
| R12 | `mem` 摘要（place_id＋時間戳）會送到伺服器 | 隱私 | 伺服器不落地、log 不記 place_id；同意畫面要寫明 |

### 假設（需要驗證，不是已知事實）

- H1：老闆大多在少數幾個固定地點（公司、住家）使用「吃」，所以「同一位置」的情境占主要使用量。
